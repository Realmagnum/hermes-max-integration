# Групповой доступ и идентификаторы MAX

## Как узнать ID пользователей и групп

В проверенном Core допущенный пользователь может отправить `/whoami` в личку боту и увидеть свой ID. Эта команда сначала проходит авторизацию плагина: пользователь, отсутствующий в `MAX_ALLOWED_USERS`, её не получит. Не открывайте бота всем ради получения ID.

Нового пользователя попросите отправить безобидное личное сообщение боту. Оператор шлюза может временно включить DEBUG для логгера плагина и найти в существующем журнале `MAX: ignoring message from unauthorized user <ID>`, затем вернуть уровень логирования. Эта запись содержит только ID запрещённого отправителя. Не публикуйте весь журнал и не включайте HTTP wire logging. Каноническое поле входящего события — `message.sender.user_id`; для кнопок — `callback.user.user_id`.

Для получения ID группы оставьте групповой доступ закрытым и попросите уже глобально разрешённого пользователя написать в группу безобидное сообщение. На уровне INFO плагин пишет `MAX: group message blocked: policy=allowlist user=<USER_ID> chat=<CHAT_ID>`. Так можно получить оба ID, не передавая запрос агенту. Если доступ в группу уже открыт, используйте существующую диагностику событий оператора: группу определяет `message.recipient.chat_id`. Событие `bot_added` также содержит `chat_id`; поле `user` в нём обозначает добавившего бота человека, а не всех участников. Плагин не ведёт каталог групп.

В `MAX_ALLOWED_USERS`, `MAX_GROUP_ALLOWED_USERS` и `MAX_GROUP_ALLOWED_CHATS` указывайте числовые ID, сохраняя знак минус при его наличии. Префиксы `user:` и `chat:` нужны для адресов доставки вроде `MAX_HOME_CHANNEL`, в этих списках они не нужны. У личного диалога тоже есть служебный chat ID: `recipient.chat_type=dialog` определяет личку, а не группу.

У MAX сейчас нет готового API со списком всех групп/каналов бота. Используйте уже работающий приёмник шлюза; не запускайте конкурирующий `GET /updates` и не заменяйте webhook-подписки только ради ID. Официальные контракты проверены 2026-10-22: [получение ID](https://dev.max.ru/docs-api/use-cases/getting-chat-id), [Update](https://dev.max.ru/docs-api/objects/Update), [Message](https://dev.max.ru/docs-api/objects/Message). `/whoami` проверена по Core `ca13a7828acd2ba8c75e1c1d1694cbc1aee7df3f`; старые версии Core могут отличаться.

## Доверенная семья и смешанные группы

В обоих сценариях используются явные списки. Замените заполнители числовыми ID; в списках пользователей должны быть только доверенные люди, даже если в группе есть другие участники.

```bash
MAX_ALLOW_ALL_USERS=false
MAX_ALLOWED_USERS=OWNER_ID,TRUSTED_ID_1,TRUSTED_ID_2
MAX_GROUP_POLICY=allowlist
MAX_GROUP_ALLOWED_USERS=OWNER_ID,TRUSTED_ID_1,TRUSTED_ID_2
MAX_GROUP_ALLOWED_CHATS=GROUP_ID
```

В семейной группе перечислите каждого, кому доверяете доступ к агенту/инструментам профиля Hermes. В смешанной группе не включайте посторонних: их сообщения, команды и нажатия кнопок будут отклонены. Участие в MAX-группе или статус администратора не дают доступ к агенту автоматически. Даже допущенный пользователь не может нажимать подтверждения или выбирать ответ за другого инициатора.

Порядок проверок: общий доступ пользователя, затем групповой доступ, затем проверки конкретного действия. `MAX_GROUP_POLICY=closed` запрещает весь групповой ввод; `open` пропускает только групповой фильтр. При `allowlist` каждый заполненный список должен совпасть (AND); один пустой список не ограничивает своё измерение, но оба пустых списка запрещают весь групповой ввод. Только список чатов допускает в них любого глобально разрешённого пользователя; только список пользователей допускает этих людей в любых группах. Списки общие для бота: отдельных списков пользователей по группам нет. Кнопки проверяют текущую политику до потребления ожидания; запрещённое нажатие оставляет его активным до обычного истечения срока.

## Контекст, приватность и полномочия агента

Все участники группы видят ответы бота и отправленные файлы, включая тех, кому запрещено давать задания. Для приватных задач используйте личку. Персональные групповые сессии разделяют контекст при Core `group_sessions_per_user=true` (проверенное значение по умолчанию); это не изоляция файлов, учётных данных или инструментов. Список доступа плагина даёт доступ к общему профилю Hermes, а не к урезанной семейной роли. Администрирование slash-команд Core — отдельная политика; доверие плагина не делает человека администратором Core автоматически.

Оставляйте в `MAX_CROSS_SESSION_USERS` только владельцев, которым разрешена история всех платформ. Не копируйте туда семейный список автоматически. Поиск личных сессий и переключение выполняйте в личке, если результаты должны быть приватными. Плагин не предоставляет MAX-фильтр «только по упоминанию»; не считайте @упоминание обязательным условием обработки. Для разных полномочий инструментов или разных людей в каждой группе используйте отдельно настроенные профили/ботов с независимыми ресурсами.

## Значения при первой установке

Новый адаптер и CLI-настройка используют следующие безопасные значения. CLI явно записывает отсутствующие параметры и сохраняет существующие групповые настройки и настройки сессий при повторной настройке. Desktop показывает групповую политику/списки и публичный URL webhook; пустое поле использует значение runtime по умолчанию.

| Переменная | Начальное значение | Следствие |
|---|---|---|
| `MAX_ALLOW_ALL_USERS` | `false` | Нужен общий список пользователей |
| `MAX_ALLOWED_USERS` | пусто до ввода | Входящие пользователи не допускаются |
| `MAX_GROUP_POLICY` | `allowlist` | Нужны явные групповые разрешения |
| `MAX_GROUP_ALLOWED_USERS` | пусто | Ограничение по пользователю не задано |
| `MAX_GROUP_ALLOWED_CHATS` | пусто | Вместе с пустыми пользователями блокирует группы |
| `MAX_CROSS_SESSION` | `false` | По умолчанию команды сессий Core |
| `MAX_CROSS_SESSION_USERS` | пусто | Явные владельцы picker не заданы |
| `MAX_SESSIONS_LIMIT` | `10` | Лимит списка/поиска |
| `MAX_SESSIONS_DEFAULT_ALL` | `false` | По умолчанию только MAX при включённом picker |

При установке только с токеном события принимаются, но запросы агенту отклоняются до настройки доступа пользователей. CLI предупреждает, если ID не введены. Групповой доступ и owner picker включаются позже осознанно. Пустой `MAX_WEBHOOK_URL` выбирает polling; host/port/path сами по себе не включают webhook. Настройка транспорта и owner picker описана в [установке](setup_RU.md). Изменения применяются после reload/restart шлюза штатным способом активного профиля.
