## Назначение и границы

Когда параллельная/фоновая сессия Hermes создаёт видимый пользователю результат ассистента, связанный с владельцем MAX, отправлять отдельное короткое уведомление в его MAX DM с названием сессии и inline-кнопкой «Открыть сессию». При нажатии показать первое пользовательское сообщение сессии и последнее видимое пользователю сообщение/результат, вызвавшее уведомление, а затем переключить активный gateway-контекст на эту сессию, чтобы следующие обращения использовали её контекст.

Уведомление — отдельное сообщение бота, а не системный toast ОС и не вход модели. Сохранить проверки callback по владельцу, чату, исходному сообщению и сроку действия, а также Core-авторизацию возобновления сессии. Не уведомлять произвольных пользователей и не раскрывать чужие сессии. Обычная доставка результата в текущую сессию не меняется, если пользователь явно не включил или не выбрал это поведение.

## Ограничения проектирования и результаты исследования

- Bot API MAX документирует inline-кнопки `inline_keyboard`; нажатие приходит как `message_callback`. `POST /answers` может ответить на callback и изменить сообщение. Официальные источники: https://dev.max.ru/docs-api/use-cases/sending-messages/keyboard/ , https://dev.max.ru/docs-api/objects/Update/ , https://dev.max.ru/docs-api/methods/POST/answers (проверено 2026-11-19).
- В MAX-плагине уже есть диспетчеризация callback, ограниченное владельцем/чатом/сообщением/TTL состояние интеракций, выбор сессии и извлечение первого/последнего контекста, генерация события `/resume --all`. Использовать существующие механизмы, не вводить параллельную схему авторизации.
- Hermes Core направляет завершения фоновых процессов/delegation в owning session через `gateway/run_notifications.py`; текущий MAX `send()` отправляет обычный текст и не имеет контракта передачи карточки/кнопки сессии. Нужен seam Core→adapter со стабильным ID возобновляемой сессии и результатом/названием либо эквивалентная возможность адаптера. До реализации подтвердить конкретные producers и пути доставки для каждого поддерживаемого типа (background process и async delegation); нельзя считать, что любая дочерняя сессия может возобновляться независимо.
- Для существующего `/resume --all` предусмотрена граница владелец/admin. Переключение из callback обязано использовать действующую политику и не ослаблять межплатформенную или посессионную авторизацию.
- Содержимое уведомления ограничено коротким заголовком/summary; карточка после нажатия показывает первое пользовательское сообщение и последний видимый пользователю результат (с безопасным усечением под лимит MAX). Не раскрывать tool-транскрипт или внутренние маркеры уведомлений как последний результат.
