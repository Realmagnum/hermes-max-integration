# Умная пагинация длинных сообщений в MAX — микроспецификация

[English version](20261024-smart-document-pagination.md)

Дата: 2026-10-24. Статус: специфицировано; реализация не начата. Источник: запрос пользователя после наблюдения обрезки cron-вывода в MAX. Базовый коммит: актуальный upstream `main` (`78d9abf`). Область действия: только плагин MAX, пока проверка не докажет необходимость изменений в Core.

## Проблема

Длинный вывод cron-задач и отчетов обрезается до попадания в плагин MAX. В ядре Hermes Core `gateway/delivery.py::_cap_oversized_output()` сверяет длину с `MAX_PLATFORM_OUTPUT` и передает сверхлимитный текст дальше только в том случае, если используемый адаптер объявляет `splits_long_messages = True`. Плагин MAX сейчас эту возможность не объявляет. В результате он получает урезанный текст со служебным футером обрезки и ссылкой на файл аудита, и уже не может восстановить потерянное.

В основном пути адаптера плагина уже есть нумерованная разбивка без потерь (`_numbered_outbound_chunks`) с номинальным бюджетом 3900 символов, но разбиение ориентируется только на строки и слова, не учитывая структуру документа. Путь самостоятельной отправки (standalone sender) также жестко срезает текст до `MAX_MESSAGE_LENGTH` (4000), потенциально отбрасывая остаток. Эти пути требуют отдельной проверки и единого поведенческого контракта.

## Цель

Обеспечить доставку длинных текстовых документов через MAX в виде упорядоченных, нумерованных страниц в пределах подтвержденного лимита платформы. Сохранять 100% исходного содержимого и делать границы разбиения удобными для чтения: отдавать приоритет полным Markdown-разделам/заголовкам и тематическим блокам, затем абзацам, затем цельным предложениям, затем строкам и словам. Жесткое разбиение применять только тогда, когда ни одна безопасная граница не помещается. Никогда не терять и не искажать исходный текст.

## Не входит в задачу

- Преобразование сообщений в HTML или картинки как обязательное условие; поддержка HTML со стороны MAX или Hermes пока не подтверждена.
- Изменение Hermes Core, его глобального лимита или других платформенных адаптеров без доказательств того, что плагин не может решить задачу объявлением своей возможности.
- Суммаризация, переписывание или пропуск содержимого ради укладывания в страницу.
- Гарантия неделимости раздела документа, если сам раздел больше лимита платформы.

## Методика реализации

1. **Проверка актуального апстрима.** Выполнить fetch `main` из Gitea и зеркала GitHub, сравнить SHA, проверить текущие `plugin.yaml`, регистрацию адаптера, `MaxAdapter.send`, `_numbered_outbound_chunks`, standalone sender и ядро `gateway/delivery.py::_cap_oversized_output`. Не начинать работу со старой ветки и не полагаться на устаревшие предположения.
2. **Подтверждение места обрезки отдельным тестом.** Воспроизвести доставку вывода cron >4000 символов и проверить, передает ли ядро полный текст в адаптер MAX. Отдельно проверить путь адаптера и путь `send_message_handler`/`standalone_sender_fn`; не предполагать автоматически, что флаг адаптера защищает независимые хуки плагина.
3. **Уточнение реальных ограничений MAX API.** Сверить официальную документацию MAX Bot API на предмет семантики подсчета длины текста, режима разметки и порядка доставки нескольких сообщений. При сомнениях провести проверку через тестового бота. Не переключаться на HTML без подтверждения поддержки со стороны API и отдельного контракта рендеринга.
4. **TDD: тесты пишутся первыми.** Покрыть тестами проброс флага из Core, пагинацию адаптера, пагинацию standalone, посимвольное восстановление оригинала, приоритеты разделов/абзацев/предложений, блоки кода, границы Unicode и сценарии частичных сбоев. Существующие тесты разбиения служат базой регрессии — расширять, а не ослаблять их.
5. **Минимальное точечное исправление в рамках плагина.** Объявить флаг разделения длинных сообщений только там, где реально реализована разбивка. Вынести логику разделения в общий хелпер плагина, доступный и для `MaxAdapter.send`, и для standalone. Применить детерминированную иерархию границ (раздел → абзац → предложение → строка → слово → жесткий срез), выбирая самую позднюю безопасную границу в рамках бюджета страницы. Учитывать длину префикса нумерации в расчете бюджета. Сохранять срезы оригинала точно, без произвольной нормализации пробелов.
6. **Аккуратная работа с Markdown.** Не использовать хрупкие регулярные выражения для поиска предложений внутри инлайн-кода, блоков кода, ссылок, таблиц и цитат. Добавить синтаксический сканер с учетом состояния или ограничить поиск предложений только безопасным неформатированным текстом; при неоднозначности откатываться к границам строк и слов. Если применяется синтетическое закрытие/открытие блоков кода, проверять как валидность отображения, так и точное восстановление оригинала.
7. **Последовательная отправка и обработка сбоев.** Отправлять страницы строго последовательно. Сохранять идентификаторы сообщений платформы. При ошибке возвращать статус частичной доставки; не повторять весь документ целиком во избежание дублирования уже доставленных страниц.
8. **Прохождение проверочных скриптов и аудит diff.** Прогнать целевые тесты пагинации и standalone, весь набор тестов плагина, `ruff check .`, `python3 scripts/check_docs_links.py`, `python3 scripts/check-ru-en-parity.py`, `python3 scripts/check-doc-claims.py` и `python3 scripts/check-config-reference.py`. Обновлять двуязычную документацию, changelog и backlog только при наличии подтвержденных результатов тестов.
9. **Рабочий процесс в Git.** Работать в чистой ветке от свежего апстрима `main`; не добавлять в коммит посторонние рабочие файлы. Пушить строго целевую ветку в нужный remote, проверять удаленный SHA и честно отражать статус CI.

## Критерий приемки

Задача считается выполненной только тогда, когда сверхлимитный cron-документ полностью приходит в MAX в виде пронумерованных сообщений в пределах лимита платформы; границы чанков отдают приоритет смысловой структуре; соединение страниц после удаления префиксов восстанавливает оригинал байт-в-байт; standalone-отправка не обрезает текст; а частичные ошибки доставляются честно. Прохождение локального юнит-теста само по себе не является достаточным доказательством сквозного пути cron из Core в плагин.
