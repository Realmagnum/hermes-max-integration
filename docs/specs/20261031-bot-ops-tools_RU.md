# Инструменты операций с ботом MAX (история, чаты, участники, пины) — Micro-Spec

Источник: запрос оператора, 2026-10-31. Базовая точка: `78d9abf`. Core: живое дерево `/home/magnum/.hermes/hermes-agent` (Core ≥ 0.21.4).

Область: добавить набор инструментов плагина, открывающий операции MAX Bot API, которые адаптер сейчас не использует — история сообщений, метаданные чатов, участники и администраторы, пины. Чтение включено по умолчанию; изменяющие операции — по явному опт-ину и только владельцу. Семантика существующего адаптера (приём/отправка, чанкинг, медиа, колбэки) не меняется.

## Почему эта точка расширения

`send_message`/`hermes send` уже закрывают исходящую доставку, адаптер — входящий поток. Чего агент сегодня не может: *смотреть и администрировать* чат — читать то, что было до его входа, перечислять свои чаты, узнавать администраторов, закреплять решение. Это обычные вызовы Bot API (`GET /messages`, `GET /chats`, `GET /chats/{id}/members`, `POST .../members/admins`, `PUT /chats/{id}/pin`), а не новый транспорт, поэтому их место — инструмент плагина, не Core и не отдельный MCP-сервер.

## Вне области

- Никакого нового ingress: `get_updates` не выставляется как polling-инструмент — поток апдейтов принадлежит адаптеру, второй потребитель будет красть апдейты у него.
- Никакой загрузки/выгрузки медиа через эти инструменты; `MEDIA:` и медиа-mixin адаптера остаются единственным путём.
- Никаких правок Core и переопределения существующих имён инструментов.

## План доказательств

1. Unit: `tests/test_ops.py` зелёный на живом дереве Core; существующий набор не меняется (отправка не затрагивается).
2. Живое чтение реальным токеном по одному групповому чату, где бот уже состоит: `get_chats` → `get_chat` → `get_members` → `get_messages(count=5)`; фиксируются идентификаторы и время, тела сообщений — нет.
3. Изменяющие операции проверяются только на одноразовом чате с явным разрешением оператора; `remove_admin`, вернувший `success: true` без фактического эффекта, считается багом на стороне API, а не успехом.
