# Правила документации

Храните в `docs/` устойчивые, нетривиальные сведения о поведении и устройстве плагина — контекст, который трудно восстановить из имени функции или очевидного кода.

## Навигация

В начале задачи выполните `tree docs`. Имена файлов — основная карта: называйте их по вопросу, на который они отвечают, например `webhook-lifecycle.md`, `media-security.md`, `desktop-sessions.md`. Если `tree` отсутствует, используйте `find docs -maxdepth 2 -type f | sort`.

Открывайте заметку по теме перед изменением соответствующей части кода. Не предполагайте, что полное дерево автоматически загружается в контекст: это зависит от агента и окружения. Если детали важны, явно прочитайте файл.

## Что документировать

- Нетривиальные инварианты, границы доверия, порядок жизненного цикла и причины решений.
- Контракты MAX/Hermes API, если схемы или типов недостаточно.
- Краевые случаи, ограничения платформы и проверенные способы диагностики.
- Изменчивые внешние утверждения с источником и датой проверки.

Не пересказывайте очевидный код, не копируйте реализации целиком и не используйте заметки вместо `CHANGELOG.md` для истории релизов.

## Разделение документации

- `docs/` — долговременные сведения о системе и её контрактах.
- `README.md` — краткое введение на английском; `README_RU.md` — русский перевод.
- `skills/` — воспроизводимые процедуры агента: prerequisites, команды, проверки, rollback и условия эскалации. Skill не заменяет заметки об устройстве системы.
- `AGENTS.md` — краткие правила навигации и работы в репозитории, не дублирующий справочник функций.
- `BACKLOG.md` — будущая работа; завершённые задачи не должны оставаться roadmap.

## Языки

Основные документы имеют английские имена, например `name.md`; русские версии называются `name_RU.md`. README подчиняется тому же правилу: `README.md` — английский, `README_RU.md` — русский. Обновляйте обе версии одновременно. Parity-checker проверяет уровни и порядок заголовков, форму таблиц, языки fenced-блоков, имена переменных окружения и ссылки на нужную языковую версию. Команды и идентификаторы не переводите.

## Обновление и проверка

При обновлении документации:

1. Сверяйте утверждения с кодом, тестами, metadata и актуальными upstream-контрактами; старый документ не является источником истины.
2. Удаляйте устаревшие инструкции, предварительно перенеся нужное содержимое в правильный документ.
3. Не помещайте токены, персональные данные и реальные адреса получателей в документацию и примеры.
4. Не отправляйте реальные сообщения и не меняйте внешнюю инфраструктуру во время проверки документации.
5. Запускайте `python scripts/check_docs_links.py`, `python scripts/check-ru-en-parity.py`, `python scripts/check-doc-claims.py`, `python scripts/check-config-reference.py`, затем релевантные тесты.

Пишите Markdown без ручного переноса строк внутри абзацев. Таблицы используйте только для действительно табличных справочников. Внутренние ссылки делайте относительными, без начального `/` и без `../`, если подходит путь от корня репозитория. Не скрывайте неопределённость; для внешних и зависящих от версии утверждений указывайте источник и дату проверки.
